Standard attention keeps a separate contiguous KV cache for each sequence. Paged attention splits the cache into fixed-size blocks and assigns them on demand from a central pool, so concurrent sequences share a predictable cache budget.

Paged attention is enabled by default for supported CUDA and Metal models. Start with automatic memory sizing: the engine plans model placement, execution workspace, and the KV pool together.

<Tabs>
<TabItem label="CLI">

```bash
# Automatic placement and memory sizing
mistralrs serve -m Qwen/Qwen3-4B

# Set an explicit shared KV cache capacity
mistralrs serve --kv-cache 8GiB -m Qwen/Qwen3-4B

# Force off
mistralrs serve --paged-attn off -m Qwen/Qwen3-4B
```

`--paged-attn` accepts `auto` (default), `on`, or `off`. `auto` enables paged attention on CUDA and Metal and disables it on CPU.

</TabItem>

```python
from mistralrs import Runner, Which

runner = Runner(
```

## Memory budget

Leave memory settings unset to use `Auto`. The engine leaves headroom for the system, reserves space for model weights and temporary computation, and uses the remaining budget for the KV cache. CLI, Python, and Rust use the same policy.

To set the engine's budget yourself, use `--gpu-memory-utilization 0.9`. This allows weights, temporary computation, and KV cache together to use up to 90% of physical GPU memory, subject to current availability and device limits.

To set just the KV capacity, use `--kv-cache 4GiB` for a byte budget or `--kv-cache 65536tokens` for a token capacity. The cache is shared across requests, and byte budgets cover all of the model's devices. Choose either `--kv-cache` or `--gpu-memory-utilization`.

Use `--max-model-len` to limit each request's prompt plus output, and `--max-seqs` to limit concurrent requests. A shared cache of 65,536 tokens does not give every request that capacity. See [throughput tuning](/guides/perf/throughput-tuning/) for these controls.

Explicit memory goals require supported paging and fail if the requested allocation cannot fit. Remove the override to return to automatic sizing.

### Automatic sizing

On discrete GPUs, `Auto` leaves the larger of 5% of physical memory or 1 GiB as headroom. On unified-memory devices, it leaves 25%, capped at 16 GiB. Metal also respects its recommended working-set limit and currently available system memory. For example, a 64 GiB Mac has a 48 GiB engine ceiling; other applications can reduce the usable capacity further.

The planner accounts for serving concurrency and prompt-processing limits. Increasing them can require more temporary memory and leave less room for the cache. Long cached prefixes may also need smaller batches to fit. These estimates guide allocation; the engine checks available memory before running each batch.

### Explicit capacity and utilization

Byte budgets allocate whole cache blocks within the requested limit. Metal also includes hardware buffer rounding in this budget; CUDA uses logical buffer bytes. Alignment and the reserved cache block can make usable token capacity lower than a simple bytes-per-token estimate. Token budgets round up to whole usable blocks and check the additional reserved block and allocation overhead against the device budget.

### Multiple models

For [multi-model serving](/guides/serve/multiple-models/), each model receives a fixed share of the initial per-device memory budget, weighted by its maximum serving concurrency. Its weights, workspace, and KV pool must fit within that share. A utilization override becomes the shared engine target, including models using `Auto`; conflicting utilization overrides are rejected. Models with paging disabled count toward the share calculation, but their placement and growing dense caches are not bounded by these paged-cache quotas. Explicit KV capacities are preserved in full; a capacity that exceeds the model's share fails instead of being silently reduced.

In Rust, set memory goals before calling `plan_paged_kv`. Changing a goal on a planned configuration requires re-planning the group.

### Cache and scheduler controls

Two more flags tune the cache itself:

- `--pa-block-size <n>`: block size (default 32).
- `--pa-cache-type`: KV cache quantization (`auto` or `f8e4m3`). This is separate from model-weight quantization (`--quant`/`--isq`); the two are chosen independently.

Scheduler memory and latency are controlled independently:

- `--max-num-batched-tokens <n>`: total scheduler-step token budget (default 4096).
- `--max-prefill-chunk-tokens <n>`: batch-wide chunkable CUDA or Metal text-prompt quantum (default 512).
- `--max-decode-steps-before-prefill <n>`: maximum decode turns before a waiting prompt receives service (default 8).

See the [serve flag reference](/reference/cli/serve/) for memory and paging flags.

Raw-logit, adapter, and multimodal prompt paths that cannot be split remain atomic. The prefill
chunk limit does not change CPU scheduling.

## How it works

The default block size is 32 tokens. Supported block sizes are 8, 16, and 32; other values fail to load because the attention kernel dispatches on block size explicitly.

Each sequence holds a list of block pointers. On each decoding step, the scheduler checks whether the sequence has a free slot in its tail block; if not, it allocates a new block from the pool. When a sequence finishes, its blocks return to the pool.

Sequences that begin with identical tokens share the blocks holding those tokens. A shared block is reference-counted rather than duplicated. This is the mechanism behind [prefix caching](/guides/perf/throughput-tuning/) when paged attention is on.

MLA (Multi-head Latent Attention)'s latent cache is supported through a dedicated kernel path. Some models opt out of the FlashInfer paged cache layout (FlashInfer is NVIDIA's attention-kernel library; see [Flash attention vs FlashInfer](#flash-attention-vs-flashinfer) below) when their cache shape needs a different backend.

## Metal prefill and decode

Metal defaults to a paged cache with contiguous head dimensions for both K and V. Short-context decode and grouped, partitioned decode use dedicated kernels. Sliding-window decode reads the visible tokens directly from the pages.

Native paged prefill handles fresh prompts, cached prefixes, and prompt chunks through the same interface. It supports uneven sequence lengths, grouped-query attention, shared KV, causal and bidirectional windows, fixed attention chunks, and multimodal bidirectional ranges. FP16, BF16, and FP32 activations can read regular or FP8 KV caches; positional biases, softcap, sinks, and explicit additive masks are applied within attention. Kernel selection follows attention dimensions and features rather than model names.

Structured masks are passed as lengths, positions, windows, and ranges. An explicitly supplied arbitrary mask can still consume substantial memory, but the kernel reads it directly without creating a full attention-score matrix. Dedicated layouts such as MLA retain their separate implementation and memory accounting.

To select the legacy Metal cache layout and decode backend before loading a model:

```bash
MISTRALRS_METAL_PAGED_LAYOUT=legacy mistralrs serve --paged-attn on -m <model>
```

The default is `MISTRALRS_METAL_PAGED_LAYOUT=hnd`; `auto` selects the same layout. The legacy option retains paging and prefix sharing. Use `--paged-attn off` to disable paging entirely. The cache layout is fixed for the lifetime of a loaded model.

## CUDA fast paths

On CUDA, paged attention dispatches to one of three paths:

- Default decode: FlashInfer-backed paged decode kernels, used when the model's KV-cache shape is compatible.
- Eligible prefill chunks: use direct paged FlashAttention, subject to compiled kernel support and request capabilities.
- Generic fallback: when a request falls outside those constraints, the runtime gathers blocks and then dispatches to the available attention backend.

CUDA prompts are chunked from the batch-wide token budget. The per-sequence chunk is the budget
divided by the admitted prompt batch size, so peak prefill work stays bounded as concurrency grows.
Chunking is internal and does not change the visible prompt, logits, or generated text.

CUDA engines retain freed scratch allocations for reuse across forward passes. Memory maintenance
trims excess cached allocations while idle and under memory pressure. Reserved CUDA memory can
therefore include reusable scratch space as well as live tensors.

`f8e4m3` stores K and V at half the bytes of BF16. CUDA accepts FP16, BF16, or FP32 activations and
converts at cache-write time; FlashInfer decode applies the K scale to logits and the V scale to
outputs without gathering a full-precision cache. Scales are immutable for the cache lifetime, so
previously written entries are never reinterpreted. The default scale is 1.0, matching the common
vLLM and SGLang serving configuration. FP8 cache is not currently supported for MLA layouts.

To compare with the non-FlashInfer paged decode path, disable the FlashInfer cache layout:

```bash
MISTRALRS_FLASHINFER_DECODE=0 mistralrs serve --paged-attn on -m <model>
```

## Flash attention vs FlashInfer

Paged attention and flash attention compose; both can be on simultaneously. They are not the same backend:

- `flash-attn` (compute capability 8.0+) and `flash-attn-v3` (Hopper) are Cargo features for the standard attention path and fallback varlen paths. See [cargo features](/reference/cargo-features/).
- FlashInfer paged decode is built with the `cuda` feature as part of paged attention. Regular FP16/BF16 paged FlashAttention prefill requires `flash-attn`; eligible FP8 FA3 paths have their own hardware and shape requirements.

Set `MISTRALRS_FLASHINFER_DECODE=0` only when debugging or comparing against the generic paged path.

## CUDA graphs

CUDA graphs capture a fixed decode step once and replay it with new token and metadata inputs. This reduces CPU launch overhead during autoregressive decoding. It does not change model math, sampling, or output quality.

They are enabled by default for supported CUDA decode paths. To disable them for comparison or debugging:

```bash
MISTRALRS_CUDA_GRAPHS=0 mistralrs serve --paged-attn on -m <model>
```

They require a CUDA build and a CUDA device, and they apply to decode, not prompt prefill.

### Replay preconditions

Graph replay is attempted only when all of these are true:

- The model implementation declares CUDA decode graph support.
- Paged attention is active.
- The step is single-token decode (`q_len == 1`), not the initial prompt chunk or a prefix-cache hit.
- The request is not using a speculative proposer path.
- The graph key matches the input shape, dtype, cache metadata shapes, and context bucket.

If any condition is not met, mistral.rs runs the normal CUDA path.

<details>
<summary>Capture and replay internals</summary>

The first time a decode shape is seen, mistral.rs runs a normal warmup forward, captures a graph for that shape, uploads it, and caches it. Later matching decode steps copy the current input ids and paged-attention metadata into graph-owned buffers and replay the graph.

Supported pipelines also capture common batch sizes during startup. Ordinary single-token FlashInfer decode reserves metadata capacity through 2048 context tokens, bounded by the available cache and sliding window. This lets startup graphs handle changing admission and drain batches within that capacity. It adds a bounded amount of attention scratch memory; longer contexts can still require another capture.

The decode graph cache holds a small number of recent graph entries. New batch sizes, tensor shapes, or metadata layouts can trigger another capture.

In multi-model groups, retained graphs must leave room for the other models' reserved forward workspace. Capture waits until every paged member has finished loading. Groups containing models with paging disabled skip capture because those models have no complete runtime memory plan. Pressure from another model's reservation defers capture to the memory-admitted normal CUDA path without permanently disabling graphs.

Other capture or replay failures disable CUDA graphs for that loaded pipeline and log a warning. Generation continues through the normal CUDA path only if memory admission succeeds; a request whose own forward workspace cannot fit is rejected.

</details>

### When graphs help

CUDA graphs help most when decode is limited by CPU launch overhead or many small kernels. They are most useful with paged attention because the paged metadata gives the graph stable tensor shapes while the values inside those tensors change from step to step. They usually do little for prompt prefill, where larger matrix and attention kernels dominate.

For apples-to-apples benchmarking, keep the same prompt length, generation length, batch size, paged-attention mode, and FlashInfer setting across runs.
